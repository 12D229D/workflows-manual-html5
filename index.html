Fundamentos

Introducción a los Workflows

Un workflow es la secuencia ordenada de pasos que un equipo sigue para entregar valor de forma repetible. Esta guía documenta una metodología de 10 bloques canónicos aplicable a cualquier workflow de desarrollo de software.

¿Qué encontrarás en esta guía?

Cada workflow documentado sigue la misma estructura, para que puedas compararlos en igualdad de condiciones y elegir el que mejor encaje con tu equipo, proyecto y contexto.

Los 10 bloques canónicos

Esta es la plantilla metodológica que se aplica a cada workflow:

1

Objetivo

Para qué existe el workflow y qué problema resuelve.

2

Cuándo utilizarlo

Contextos y escenarios donde encaja, y donde no.

3

Roles y responsabilidades

Quién hace qué en cada fase del workflow.

4

Pasos detallados

La secuencia operativa paso a paso.

5

Herramientas involucradas

6

Plantillas / ejemplos

Recursos copiables para arrancar rápido.

7

Puntos de control

Gates de calidad que frenan o permiten avanzar.

8

9

Métricas de éxito

Cómo medir si el workflow funciona.

10

Workflow

Git Flow

Flujo de ramas clásico de Vincent Driessen, ideal para productos con releases planificados y versionado semántico estricto.

1 Objetivo

Garantizar un historial de versiones predecible en proyectos con ciclos de release largos, separando claramente desarrollo, integración, releases y hotfixes.

ℹ️
Git Flow resuelve la tensión entre "desarrollo continuo" y "releases estabilizadas" aislando cada preocupación en su propia rama.

2 Cuándo utilizarlo

✅ Úsalo cuando

  • Hay releases planificados (p. ej. móvil, desktop, SaaS on-prem).
  • Mantienes varias versiones en producción a la vez.
  • Necesitas hotfixes a una release sin tocar desarrollo.

⛔ Evítalo cuando

  • Haces despliegues continuos (CD con muchos deploys al día).
  • Equipo pequeño con flujos de feature simples.
  • Producto web SaaS sin versionado expuesto al usuario.

3 Roles y responsabilidades

Rol Responsabilidad en el workflow
Maintainer del repositorio Aprueba merges a main y develop, gestiona tags de release.
Release Manager Abre la rama release/*, estabiliza, publica y mergea de vuelta.
Desarrollador/a Crea feature/* desde develop, abre PR, resuelve feedback.
QA Valida la rama release/* antes de subir a main.

4 Pasos detallados

  1. develop contiene el estado "siguiente release".
  2. Nueva feature: git checkout -b feature/login develop.
  3. Desarrollo + commits regulares; rebase ocasional sobre develop.
  4. Finaliza feature: PR a develop → merge --no-ff.
  5. Inicio de release: git checkout -b release/1.4.0 develop.
  6. Solo fixes de estabilización en release/*; bump de versión.
  7. Merge release/* a main (tag v1.4.0) y a develop.
  8. Hotfix: git checkout -b hotfix/1.4.1 main; merge a main (tag) y a develop.

5 Herramientas involucradas

git-flow

Extensión CLI que automatiza las ramas y tags.

GitHub / GitLab

Plataforma de PRs y protection rules por rama.

SemVer

Versionado semántico MAJOR.MINOR.PATCH.

CHANGELOG.md

Registro humano de cambios por release.

6 Plantillas / ejemplos

Comando para inicializar el repositorio con la extensión git-flow:

bash 
git flow init -d
git flow feature start login
# ... desarrollo ...
git flow feature finish login

git flow release start 1.4.0
# ... estabilización ...
git flow release finish 1.4.0

7 Puntos de control

  • Gate 1 PR de feature → CI verde + 1 revisor antes de merge a develop.
  • Gate 2 Rama release/* → QA sign-off antes de llegar a main.
  • Gate 3 Hotfix → regression tests + tag + backport a develop simultáneo.

8 Errores frecuentes

⚠️
  • Merge directo en main sin pasar por release/*: rompe el aislamiento de estabilización.
  • Olvidar el merge back de un hotfix a develop: el bug reaparece en la siguiente release.
  • Features largas que viven semanas fuera de develop: conflictos masivos al integrar.
  • No tagear releases: imposible reproducir una versión exacta.

9 Métricas de éxito

< 24h Lead time hotfix
0 Releases sin tag
≥ 1 Revisor por PR

Trunk-Based Development

Todas las integraciones van a main (o trunk) de forma frecuente y corta. Es la base del Continuous Integration y del CD.

1 Objetivo

Minimizar el coste de integración manteniendo main siempre liberable. Las features se vuelven pequeñas, integradas y ocultadas por feature flags hasta estar listas.

2 Cuándo utilizarlo

✅ Úsalo cuando

  • Buscas CD con varios deploys al día.
  • Confías en feature flags para desacoplar deploy de release.
  • Tienes CI sólido y rápido (minutos).

⛔ Evítalo cuando

  • Releases congeladas y versionadas en paralelo.
  • Equipo sin disciplina de commits pequeños.
  • No hay CI/CD que valide cada push.

3 Roles y responsabilidades

RolResponsabilidad
Desarrollador/aBranch corta (< 24h), PR pequeño, integra a main a diario.
ReviewerResponde en < 4h; bloquear main es un anti-patrón.
Release EngineerMantiene pipeline CD y feature flag service.
On-callRecibe alertas de un deploy y puede revertir en minutos.

4 Pasos detallados

  1. git checkout -b feat/login main (rama de vida corta).
  2. Desarrollo con commits pequeños protegidos por feature flag.
  3. Push al origen → CI automático.
  4. PR a main con checks verde; revisión rápida.
  5. Merge --squash o --no-ff según convención del repo.
  6. main se deploya automáticamente (CD).
  7. Cuando la feature es estable, activa el flag por segmento y monitoriza.

5 Herramientas involucradas

Feature Flags

LaunchDarkly, Unleash, Flagsmith.

CI/CD

GitHub Actions, GitLab CI, Jenkins.

Observabilidad

Datadog, Grafana, Sentry.

Trunk

Rama main única, siempre verde.

6 Plantillas / ejemplos

Ciclo típico de una feature corta:

bash 
git checkout main && git pull --rebase
git checkout -b feat/login-button

# ... realiza commits pequeños ...

git push -u origin feat/login-button
# Abre PR → revisión → CI verde → merge --squash a main

# main se deploya solo; activa feature flag vía consola

7 Puntos de control

  • Gate 1 PR pequeño (< 400 LOC) + CI en < 10 min.
  • Gate 2 Feature cubierta por tests; main siempre verde.
  • Gate 3 Rollback automático ante alertas post-deploy.

8 Errores frecuentes

⚠️
  • Ramas largas (> 2 días) que rompen la premisa del trunk.
  • Deploy = release sin feature flags: miedo a integrar incompleto.
  • CI lento (> 30 min): la gente deja de integrar a menudo.
  • Revertir es difícil: se acumula deuda operativa.

9 Métricas de éxito

> 1/día Integraciones por dev
< 10 min Pipeline CI
< 5 min MTTR deploy

Workflow

GitHub Flow

Flujo liviano y flexible basado en **Pull Requests** hacia una única rama principal (main). Diseñado para despliegues continuos y comunicación fluida en equipo.

1 Objetivo

Eliminar la sobrecarga de gestión de múltiples ramas estables (como en Git Flow), permitiendo enviar cambios probados a producción de forma rápida y transparente.

ℹ️
En GitHub Flow, todo lo que está en la rama main es desplegable a producción en cualquier momento.

2 Cuándo utilizarlo

✅ Úsalo cuando

  • Desarrollas aplicaciones web SaaS, APIs o microservicios.
  • Publicas cambios a producción de manera frecuente (diario o semanal).
  • Deseas discusiones abiertas y revisiones claras mediante Pull Requests.

⛔ Evítalo cuando

  • Necesitas soportar múltiples versiones antiguas en paralelo.
  • Hay ciclos de QA manual extensos (semanas) antes de desplegar.
  • Software empaquetado descargable con fechas fijas de versión.

3 Roles y responsabilidades

RolResponsabilidad
Desarrollador/aCrea rama con nombre descriptivo, envía commits y abre PR temprano.
Revisor / PeerRevisa el código, prueba en preview environment y aprueba la PR.
Automation / CIEjecuta linters, pruebas unitarias y construye previews en cada push.
Release ManagerNo existe como rol aislado; el equipo despliega al hacer merge.

4 Pasos detallados

  1. Crea una rama descriptiva desde main (ej. feat/add-stripe-checkout).
  2. Realiza commits frecuentes con mensajes claros y descriptivos.
  3. Abre un Pull Request tan pronto como quieras discusión o revisión.
  4. Discute el código, responde revisiones y pasa las verificaciones automatizadas (CI).
  5. Despliega el entorno de preview para pruebas en vivo antes del merge.
  6. Haz merge a main y despliega inmediatamente a producción.

5 Herramientas involucradas

GitHub / PRs

Plataforma para discusión, diffs y aprobaciones.

GitHub Actions

CI/CD para pruebas unitarias y despliegue.

Preview Envs

Vercel, Netlify o Kubernetes ephemerals.

Codeowners

Asignación automática de revisores por ruta.

6 Plantillas / ejemplos

Comandos esenciales para el ciclo de GitHub Flow:

bash 
# 1. Crear rama desde main
git checkout main && git pull
git checkout -b feat/user-notifications

# 2. Guardar cambios y subir
git commit -m "feat: agregar campana de notificaciones en navbar"
git push -u origin feat/user-notifications

# 3. Tras aprobar PR en GitHub, mergear y limpiar localmente
git checkout main
git pull
git branch -d feat/user-notifications

7 Puntos de control

  • Gate 1 Branch Protection en main: deshabilita pushes directos.
  • Gate 2 Al menos 1 aprobación explícita de un par en el Pull Request.
  • Gate 3 Pipeline de CI en verde (tests, linter, security audit).

8 Errores frecuentes

⚠️
  • Abrir la PR al final del desarrollo: impide discusiones tempranas sobre arquitectura.
  • Ramas que duran semanas sin sincronizar: generan conflictos masivos al mergear.
  • Merge sin desplegar: acumular commits en main sin validar en producción.

9 Métricas de éxito

< 24h Tiempo de vida de la PR
100% PRs con CI en verde
< 300 Líneas por Pull Request

Workflow

GitLab Flow

Conecta el flujo sencillo de ramas de GitHub Flow con la gestión explícita de entornos (staging/production) o versiones de release.

1 Objetivo

Ofrecer una alternativa estructurada a Git Flow que no sacrifique la simplicidad, garantizando que cada código probado pase ordenadamente por entornos de validación antes de producción.

2 Cuándo utilizarlo

✅ Úsalo cuando

  • Cuentas con entornos físicos o virtuales estrictos (Staging, Pre-prod, Prod).
  • Necesitas desplegar versiones específicas a clientes seleccionados.
  • Deseas evitar la complejidad de la rama develop de Git Flow.

⛔ Evítalo cuando

  • Tu arquitectura permite despliegue continuo directo desde main a prod.
  • No tienes staging ni infraestructura para pruebas previas.

3 Roles y responsabilidades

RolResponsabilidad
Desarrollador/aCrea feature branch y hace Merge Request (MR) hacia main.
QA / Staging LeadValida cambios integrados en main (entorno de Staging).
Operations / Release ManagerPromueve de main a la rama production cuando se aprueba.

4 Pasos detallados

  1. Desarrolla la funcionalidad en una rama corta desde main.
  2. Abre un Merge Request (MR) apuntando hacia main.
  3. Tras revisión y CI, haz merge a main (esto despliega automáticamente a Staging).
  4. Valida la integración en el entorno de Staging.
  5. Para llevar a Producción, abre un MR o promueve el commit desde main hacia la rama production.

5 Herramientas involucradas

GitLab CI/CD

Pipelines avanzados con entornos y variables.

Merge Requests

Herramienta de revisión de código de GitLab.

Environments

Seguimiento de despliegues por rama en GitLab UI.

6 Plantillas / ejemplos

Flujo de promoción entre ramas de entorno:

bash 
# 1. Desarrollo e integración en main (Staging)
git checkout main
git merge --no-ff feature/checkout-v2

# 2. Promoción a producción tras validación en Staging
git checkout production
git merge main
git push origin production

7 Puntos de control

  • Gate 1 MR a main requiere aprobación de peer y CI limpio.
  • Gate 2 Testeo e integración exitosa en el entorno Staging.
  • Gate 3 Merge a production restringido a roles de Maintainer.

8 Errores frecuentes

⚠️
  • Aplicar hotfixes en production sin pasar por main (causa regresiones).
  • Saltarse el entorno de Staging introduciendo cambios no testeados.

9 Métricas de éxito

0 Commits directos en production
100% Despliegues rastreables por MR
< 1h Tiempo de promoción staging → prod

Workflow

Release Flow

Metodología empleada a gran escala (estilo Microsoft Azure DevOps). Mantiene un main siempre activo y genera ramas de release por sprint para estabilización y despliegue.

1 Objetivo

Soportar entregas periódicas (semanales o por Sprint) en equipos con decenas de desarrolladores, garantizando que el desarrollo en main nunca se detenga mientras se prepara un release.

2 Cuándo utilizarlo

✅ Úsalo cuando

  • Equipos grandes integrando código continuamente en main.
  • Cadencia de despliegue fija (ej. cada jueves o al final de cada Sprint).
  • Filosofía de solucionar bugs primero en main y luego portar al release.

⛔ Evítalo cuando

  • Proyectos pequeños con pocos cambios semanales.
  • Despliegue continuo inmediato sin ciclos de Sprint.

3 Roles y responsabilidades

RolResponsabilidad
Desarrollador/aCrea topic branches desde main y resuelve bugs siempre primero en main.
Release CommanderCrea la rama release/YYMM al final del Sprint y gestiona cherry-picks.

4 Pasos detallados

  1. Desarrolla en topic branch desde main e integra mediante Pull Request.
  2. Al final del Sprint, se crea la rama de release (ej. release/2026.07) desde main.
  3. Se despliega la rama de release a producción.
  4. Si surge un bug en producción, se soluciona primero en main y luego se hace cherry-pick a la rama de release.

5 Herramientas involucradas

Azure Pipelines / Actions

Automatización de despliegues y cherry-picks.

Git Cherry-Pick

Mecanismo para aplicar parches específicos a releases.

6 Plantillas / ejemplos

Flujo de Hotfix en Release Flow (Fix First in Main):

bash 
# 1. Corregir en main
git checkout main
git commit -m "fix: solucionar fuga de memoria en autenticación"
# Obtener el hash del commit (ej: a1b2c3d)

# 2. Portar el fix a la rama de release activa
git checkout release/2026.07
git cherry-pick a1b2c3d
git push origin release/2026.07

7 Puntos de control

  • Gate 1 Regla estricta: ningún commit ingresa a la rama de release sin existir previamente en main.
  • Gate 2 Verificación de cherry-pick automático vía bot de CI.

8 Errores frecuentes

⚠️
  • Corregir directo en la rama de release y olvidar el commit en main (causa reaparición del bug en la siguiente entrega).

9 Métricas de éxito

100% Bugfixes en main primero
0 Bugs reaparecidos en versión posterior

Asistente de Selección de Workflow

Responde a 4 preguntas clave sobre tu producto, equipo y cadencia de despliegue para obtener una recomendación personalizada del workflow ideal.

Paso 1 de 4 Tipo de Producto

1. ¿Qué tipo de producto desarrollas principalmente?

Selecciona el formato de entrega de tu aplicación.

2. ¿Con qué frecuencia despliegan o publican cambios?

Indica el ritmo habitual de entrega de valor.

3. ¿Cuántos desarrolladores trabajan en el código?

El tamaño del equipo condiciona el volumen de conflictos de integración.

4. ¿Necesitan mantener múltiples versiones antiguas en paralelo?

Por ejemplo: parches de seguridad para v1.2 mientras desarrollan v2.0.
